# AetherRSI Protocol v0.1

Status: draft. The core in this repository is the reference implementation; `conformance/` decides pass or fail.

An extension is **one folder with an `aether.json` manifest**. The core reads manifests only. It never imports extension code:
pages run in sandboxed iframes and agents run as separate processes.

## 1. Manifest

```json
{ "aether": "0.1", "kind": "preview", "id": "md-preview", "label": "Markdown", "match": [".md"], "entry": "index.html" }
```

| Field | Kinds | Rule |
|:--|:--|:--|
| `aether` | all | Protocol version. In 0.x the minor must equal the core's. From 1.0: same major, minor not newer than the core |
| `kind` | all | `preview`, `agent` or `app` |
| `id` | all | `name` or `author.name`, each part `[a-z0-9][a-z0-9-]{0,39}`. Use `author.name` for anything you share (§2.1). First one found wins; later duplicates are reported and skipped |
| `label` | all | What the UI shows |
| `entry` | preview, app | A file inside the folder (relative, no `..`) |
| `url` | app | Instead of `entry`: a page that a program on this machine serves, `http://127.0.0.1:<port>/…` (or `localhost`, `[::1]`). See §3.1 |
| `match` | preview | File extensions, e.g. `[".md", ".markdown"]`. `"*"` = a fallback: it opens only the file types no other preview matches (files without an extension included) |
| `binary` | preview | `true`: the page gets the file as bytes (`data`, an ArrayBuffer, up to 50 MB) instead of `text` (UTF-8, up to 2 MB). For pptx, images, archives |
| `command` | agent | argv list. `{dir}` = the extension folder, `{python}` = the core's Python |
| `render` | preview | argv list (`{dir}`, `{python}` as for `command`): a program that draws the file's pages as images, for what a browser cannot draw faithfully (a .pptx by LibreOffice). The core runs it, the page asks for the pages with `render`. See §3.2 |
| `inject` | agent | `true` if the agent accepts more text while running (default false) |
| `audio` | agent | `true` if the agent takes the person's voice while it runs (§4.2; default false). The shell then offers 🎙 |
| `dispatch` | agent | `true` if the agent may send messages to other agents through the core while it runs (§4.3; default false) |
| `guard` | agent | `true` if the agent honours `protect` (§4). A locked core does not run agents without it |
| `icon` | agent | A `.svg` or `.png` file inside the folder (up to 64 KB). The UI shows it in place of `label` where room is short (the label stays as the tooltip) |
| `agent_rules` | app | A file inside the folder with instructions for the agent (e.g. `CLAUDE.md`) |
| `ports` | app | Ports of servers on this machine the page may `fetch` through the shell (§3), e.g. `[8771]`. Never the core's own port |

Unknown fields are ignored. A folder whose manifest breaks a rule is skipped and listed in `/api/info` `errors`.

## 2. Where extensions live

| Kind | Found in |
|:--|:--|
| preview, agent | `<workspace>/extensions/` and `<data>/extensions/` (data defaults to `~/.aether-rsi`), as `<folder>/` or one level down as `<group>/<folder>/`. A group is a folder without `aether.json`. A group named after a kind (`preview/`, `agent/`, `app/`) only holds that kind |
| app | any folder of the workspace's file tree |
| preview, agent (machine) | the folders listed in `settings.json` `extensions` (this machine's settings, see §4.1), read after the workspace's `extensions/` and before `<data>/extensions/`, whatever the workspace is. A folder listed twice is read once |
| spare | `aether/fallback/` inside the core, read last. A spare only fills an `id` neither folder above has (a workspace without `extensions/` still gets the `claude-code` agent and the `text-preview` preview); when the workspace has the same `id`, the spare is skipped quietly. `/api/info` marks it `"spare": true` |

Install = `git clone` into one of these folders. Uninstall = delete the folder. The core rescans when the folder or a group changes.

### 2.1 Extensions from different authors

Extensions written by different people must run side by side on anyone's machine. What they could fight over, and who decides:

| They could clash on | Rule |
|:--|:--|
| Pages | Never: each page is its own sandboxed frame with an opaque origin (no shared DOM, cookies or storage) |
| Apps | Never: an app is identified by its folder, not by its `id` |
| `id` | Share with `author.name` (e.g. `ada.md-preview`). On a clash the first found wins (workspace, then data, folders in name order) and the other is listed in `/api/info` `errors` with the folder that took the id |
| A file type (two previews match `.md`) | **The person picks.** The shell offers "open with" when more than one preview matches and stores the pick in `<data>/config.json` `open_with` (`{".md": "ada.md-preview"}`). Without a pick, the first found opens |
| Shared settings (`agent`, `open_with`) | Only the person changes them, through the shell (`POST /api/config`). Extensions cannot: pages have no access to the API, and agents get the data folder in `protect` while the core is locked. `core_locked` is not writable through the API at all |

## 3. Pages (preview and app)

The core loads `entry` in `<iframe sandbox="allow-scripts allow-modals" allow="fullscreen">` and serves it with `Content-Security-Policy: sandbox allow-scripts allow-modals`.
`allow-modals` is there for `print()` (a preview's print / PDF button); `fullscreen` for a slideshow. Neither gives the page a way out of its origin.
The page therefore has an opaque origin: it cannot call the core's API, read cookies or reach the parent DOM.
Previews are served from `x/<id>/`, apps from `files/<path>/`.
Clicking an app folder (in the tree, a folder list or a link) runs the app; its files are one click away (📁 Contents).
Because the origin is opaque, the page's own requests carry no cookies, so behind an authenticating proxy they would fail.
The core therefore delivers an HTML page as **one document**: relative `<script src>`, `<link rel="stylesheet">` and `<img src>` inside
the folder are inlined, and `<script src="aether-sdk.js"></script>` becomes the SDK. Anything else (data, other files) is read with `read`.
`<script src="aether-icons.js"></script>` (before the SDK) gives the page the shell's icons: `mui("Name")` is a one-colour Material icon
(https://mui.com/material-ui/material-icons/, the text's colour) as an `<svg>`, `muiText("… {AttachFile} …")` the words with icons inside.

Messages are `postMessage` objects `{aether: "0.1", type, ...}`. The core accepts messages only from the frame it opened.

| Direction | type | Fields | Meaning |
|:--|:--|:--|:--|
| core → page | `open` | `path`, `name`, `text` (preview), `data` (preview with `binary: true`) or `folder: true` (app), `top?`, `state?`, `error?` | What to show. Sent after load. `top` is the scroll position to restore (← →); `state` is what the page last gave to `state` |
| core → page | `scroll.to` | `top` | Scroll back to `top` (← → inside the same file) |
| core → page | `rev` | `rev` | Something changed in the core (a job moved, a task changed) |
| core → page | `dest` | `task` (`{id, title}` or null) | The task the composer is addressed to |
| core → page | `theme` | `dark` | Colour scheme of the shell |
| core → page | `reply` | `id`, `ok`, `text` or `error` | Answer to `read` and `file.open` (to `fetch`: `status`, `statusText`, `contentType`, `data` (ArrayBuffer) instead of `text`) |
| page → core | `quote.add` | `label`, `text` | Add a quote chip to the composer. The person sends it |
| page → core | `send` | `text` | Put text in the composer. **Not sent**: sending is always the person's click |
| page → core | `task.open` | `id` | Open a task's conversation |
| page → core | `read` | `id`, `path` | Read a text file inside the extension's own folder (an app's folder, or a preview's `x/<id>/`) |
| page → core | `render` | `id`, `force?`, `wait?`, `page?`, `width?` | Previews with `render` in the manifest: the pages of the open file (§3.2). `reply` carries `state`, `running`, `error`, `key`, `dir`, `pages` and `data` (an ArrayBuffer per page) ―― with `page` + `width`, that page drawn larger: `name`, `file`, `data` |
| page → core | `file.open` | `id`, `path`, `hash?` | Follow a link: `path` is in the data folder (the page resolves a relative link against `open.path`). The core opens it and keeps ← → history; `reply` says whether it exists |
| page → core | `fetch` | `id`, `url`, `method?`, `body?`, `contentType?` | Apps: the shell fetches `http://127.0.0.1:<port>/…` for the page, `port` one of the manifest's `ports` (GET, or POST with a string body). Through a relay it goes to the relay's `/proxy/<port>/` with the shell's cookies ―― the sandboxed page's own requests carry none (a `SameSite=Lax` cookie is not sent from an opaque origin) |
| page → core | `url.open` | `url` | Open an `http(s)`/`mailto` link in a new tab (the frame has no `allow-popups`) |
| page → core | `scroll` | `top` | Where the page is scrolled, so ← → can come back to it |
| page → core | `download` | `name?`, `data?`, `mime?` | Download the shown file (the frame itself cannot) ―― or, with `data` (an ArrayBuffer, transferred), those bytes as `name` (a video the page encoded…) |
| page → core | `state` | `value` | Remember a small JSON value (≤ 4 KB) for this extension in this browser |
| page → core | `bar` | `items` | Put the page's own controls in the shell's bar (below). Replaces what the page put before; `[]` clears |
| core → page | `bar` | `id`, `value` | A control of the page was clicked (`value` = the picked option, or `""`) |
| core → page | `fullscreen` | `on` | The frame left (`false`) full screen that a `full` control started |
| page → core | `fullscreen` | `on: false` | End that full screen (the frame cannot: the full-screen element is in the shell's document) |

#### 3.1 The bar

The bar above the page belongs to the core: the path, ← →, “open with”, 📎 quote and 🔄 reload are always there and a page cannot
hide or relabel them. Next to them, the page that is open (a preview or an app) may put **its own controls** with `bar`:

```json
{ "type": "bar", "items": [
  { "id": "present", "icon": "Slideshow", "label": "Present", "full": true, "options": [{ "value": "simple", "label": "Simple" }] },
  { "id": "unit", "label": "Quote by", "value": "block", "select": true, "options": [{ "value": "block", "label": "Block" }, { "value": "section", "label": "Section" }] },
  { "id": "sel", "icon": "AttachFile", "label": "Quote selection", "disabled": true }
] }
```

- An item is a button. With `options` it gets a ▾ menu (the button itself sends `""`); with `select: true` it is a drop-down that sends the picked value
- An option is `{value, label, icon?, title?, full?}` (`title` shows under the label in the menu) or `{head}`, a heading line that cannot be picked
- `icon` (item or option): the name of a Material icon the shell has (`aether-icons.js`), drawn in one colour before the label. An empty label leaves
  the icon alone, named by `title`. A label that starts with an emoji the shell knows ("⬇ Download") is drawn the same way (older pages)
- `full: true` (on the item, or on one option, which wins): the core puts the frame in full screen **before** sending `bar`
  (a click in the shell does not activate the frame, so the page could not). A print / PDF option leaves `full` off
- Text only (labels and titles are set as text, never HTML). At most 6 items, 12 options each, labels up to 24 characters; the rest is dropped
- Controls belong to the frame that sent them: they go away when another file or app opens

#### 3.2 Pages drawn by a program (`render`)

A page cannot start a program, and some files can only be drawn faithfully by one. A preview may name one in `render`; the core
runs it as its own process (like an agent: it is the extension's code, so install only what you trust) and keeps what it drew under
`<data>/render/<preview id>/<hash of the path>/<file version>/`. The version is the file's mtime and size; only the newest is kept.

- The command gets `<file> <out>`: the file (absolute) and an empty folder to fill with `p-1.png`, `p-2.png`… (zero padding is fine).
  For one page at a larger width: `<file> <out> --page N --width W --base <the folder of the full render>`, W one of 1920, 2560, 3840
  (anything else gets the normal page). Exit 0 with at least one page = success; otherwise what it printed becomes `error`.
  The working directory is `<out>`. At most two run at once; one is stopped after 300 s
- It is drawn when the page asks and nothing is drawn for the file as it is now (`state: "none"`, or `"stale"` while an older
  version is shown), **when a job ends that quoted the file** (an agent probably changed it, so it is ready before anyone opens it),
  and again on `force`. The shell's 🔄 asks for `force` before it opens the file again, so one button reads the file and draws its
  pages anew; meanwhile the page gets the pages drawn before with `running: true`. A failure is not retried by itself: `force` does
- `data` reaches the page through the shell (the frame's own requests carry no cookie behind a relay). `dir` / `file` are the
  absolute paths of the images, for a quote that lets the agent look at the page
- A page should keep a way to show the file without it (the program may be missing on this machine: `error`)

#### 3.0 An app served by a program (`url`)

An app may name `url` instead of `entry`: a page that a program on this machine serves (a live viewer such as robosim-live's `live.py`).
The shell opens it in `<iframe sandbox="allow-scripts allow-same-origin allow-forms allow-modals allow-popups allow-downloads">`, so it
runs as it would in a tab of its own (modules, storage, its own requests). Only loopback hosts are allowed. Through a relay
(`…/proxy/<port>/`) the shell rewrites it to the same relay's `/proxy/<its port>/`. If that puts the page on the core's own origin, the
page could use the core's API, so the shell shows a warning and opens it only when the person presses ▶ (or offers a tab of its own).
If the program does not answer, the shell says so and offers 🔄. The page does not get the SDK's `open` message; quoting it works from the bar (📎).

## 4. Agents

The core starts `command` with the workspace as the working directory, one process per job, in its own process group.
Both directions are **JSON lines** (one object per line, UTF-8).

#### 4.1 Environment

The agent inherits the core's environment plus what `settings.json` adds: `vertex` (`credentials`, `project`, `region`) becomes
`GOOGLE_APPLICATION_CREDENTIALS`, `ANTHROPIC_VERTEX_PROJECT_ID`, `GOOGLE_CLOUD_PROJECT`, `CLOUD_ML_REGION`, `GOOGLE_CLOUD_LOCATION`,
`CLAUDE_CODE_USE_VERTEX=1` and `GOOGLE_GENAI_USE_VERTEXAI=true`; `env` adds any other name and wins over `vertex`. The file is
`settings.json` beside the core's clone (`<data>/settings.json` for a pip install, `AETHER_SETTINGS` for either), read again when it
changes. Only the key's path travels, never its contents. Bad entries are skipped and listed in `/api/info` `errors`; while the core
is locked the file is in `protect`.

core → agent (stdin):

```json
{"type": "start", "aether": "0.1", "prompt": "…", "session": "id or null", "cwd": "/abs/workspace", "protect": ["/abs/core", "/abs/data"]}
{"type": "inject", "text": "…"}
```

agent → core (stdout):

```json
{"step": "📖 README.md"}
{"step": "💻 cd /abs/path; sed -n 1,40p a.md; grep -n …", "full": "the whole command"}
{"session": "id"}
{"done": true, "reply": "…", "cost": 0.012}
{"error": "…"}
```

- `prompt` is the message followed by its quotes (`@n label` and `> text`); an app quote asks the agent to read its `agent_rules` first.
- `step` is one short line per thing the agent does. If the line cuts a longer text, `full` may carry all of it (up to 20,000 characters): the shell ends the line with … and opens the whole text on click.
- `session` is whatever the agent reported last time for the same task, so a task is one conversation.
- `inject` arrives only if the manifest says `inject: true`. The core closes stdin after `done`; text arriving later becomes the next job of the same task.
- `protect` lists folders the agent must not write to (empty when the core is unlocked). Agents declare `guard: true` to say they enforce it.
- Stop = the core sends SIGTERM (then SIGKILL) to the process group.
- Exit without `done`, or any `error` → the job fails with that message (or the tail of stderr).

#### 4.2 Voice (`audio: true`)

The person talks to a running job through the shell's 🎙. The core carries the sound both ways between the shell and the agent's
stdin/stdout. Sound is raw PCM, 16-bit little-endian, mono, base64 in the JSON line: **16 kHz from the person, 24 kHz from the agent**.

core → agent: `start` carries `"audio": true` when the message was sent from 🎙 (the person is about to speak: stay until `end`), then

```json
{"type": "audio", "data": "<base64 PCM16 16 kHz>"}
{"type": "audio", "end": true}
```

agent → core:

```json
{"audio": "<base64 PCM16 24 kHz>"}
{"heard": "what the person said"}
{"said": "what the agent said"}
{"interrupted": true}
```

- `data` arrives about every 100 ms while the mic is open. `end` = the person closed the mic: finish the conversation (the work it
  started may go on) and send `done`. A dropped connection (a reload, the network) sends nothing: the shell opens the mic again.
- `heard` / `said` are whole utterances (gather the pieces until the turn ends). The core keeps them as steps (`🎙 …` / `🔊 …`) and
  passes them to the shell; `audio` and `interrupted` (the person cut in: drop what is still to be played) only go to the shell.
- The shell's side is a WebSocket: `POST /api/jobs/<id>/audio` → `{ticket}` (single use, 30 s), then
  `GET /api/jobs/<id>/audio?ticket=…` with `Upgrade: websocket`. Binary frames are the sound (PCM16 without base64), text frames JSON:
  shell → core `{"type": "end"}`; core → shell `{"type": "wait"}` (queued), `{"type": "ready"}`, `{"heard"}`, `{"said"}`,
  `{"interrupted"}`, `{"type": "end", "state"}`. One mic per job: a second one takes over.

#### 4.3 Dispatch (`dispatch: true`)

The agent may hand work to other agents as tasks of their own, so they show in 📋 Tasks and the queue, the conflict check and the lock
apply as to a message the person sends. While its job runs it gets `AETHER_API` (the core's base URL) and `AETHER_TOKEN` (good for
that job only; a reload keeps it) and calls the core's HTTP API (§5) with `Authorization: Bearer <token>` in place of `X-Aether`:

- `POST api/send` `{text, agent, task?, quotes?, inject?}` (not `voice`, not `confirm`): a new task, the next message of a task, or ↪ into a running job
- `POST api/jobs/<id>/stop`, and the `GET` endpoints to follow what it sent (`api/jobs?task=`, `api/queue`, `api/tasks`)

Not to an agent that itself declares `dispatch` (no chains), and up to 20 sends per job; the core answers `403` past that.
Not into its own session either: it would wait for the sending job to end. A `task` of that session is dropped (a task of its own,
which starts now), and an `inject` into a job of it is `403`.
The job that sent keeps one step per send (`📨 agent: text`).

#### 4.4 The screen (agents with `audio: true`)

While the mic is open, the agent may read and drive the shell as the person sees it ―― the same browser, no other one. It asks with a
line on stdout and gets the answer on stdin; the core passes both over the mic's WebSocket:

```json
{"ui": {"id": 7, "op": "snapshot"}}
{"ui": {"id": 8, "op": "click", "n": 12}}
{"ui": {"id": 9, "op": "type", "n": 3, "text": "…", "enter": false}}
{"ui": {"id": 10, "op": "key", "keys": "Meta+Enter"}}
{"ui": {"id": 11, "op": "scroll", "n": 5, "dy": 400}}
```

```json
{"type": "ui", "id": 7, "result": {"items": [{"n": 12, "role": "button", "name": "Send to Claude Code", "area": "Send a message", "state": {}}], "dialog": "", "focus": "…"}}
{"type": "ui", "id": 8, "error": "…"}
```

- `snapshot` lists what a mouse or keyboard can use on screen now (buttons, links, fields, menus, tabs, tree rows…; not hidden, not
  covered), numbered. The numbers hold until the next snapshot. Items of the page open in the panel (a preview or an app that loads
  `aether-sdk.js`) are numbered `"f1"`, `"f2"`…; an app served by `url` without the SDK is not reachable.
- `click` refuses an item that something else covers (as a real click would). Each action flashes the item on screen.
- `key` reaches the page's own key handlers (⌘Enter, Escape, arrows); the browser's own defaults (Tab moving the focus) do not run.
- No mic open: the core answers at once with `error`.

## 5. Core HTTP API (for the shell; extensions do not call it)

All URLs are relative, so the core also works under a proxy prefix. POST requires the header `X-Aether: 1` and rejects `Origin: null`.
See the docstring of `aether/server.py` for the list of endpoints.

A task may carry a `ref` (one line, up to 300 characters): where an app keeps it, e.g. `robosim-live/sessions/12#n7-3`. The core
stores it and never reads it; the shell bundles 📋 Tasks by the part before `#` (the session). Set it with `POST /api/tasks {title, ref}`,
`POST /api/tasks/<id> {ref}` or `POST /api/send {…, ref}` when the message starts a new task.

**One task per session**: a session is a task's `ref` up to `#`, or the task alone when it has none. The first waiting job of every
session that has nothing running starts at once, each in an agent process of its own (no limit on how many sessions run); the next job
of a busy session waits for it. `/api/queue` gives a waiting job `pos`, its place in its session.
`POST /api/jobs/<id>/move {before?}` changes that order: the waiting job goes just before `before` (another waiting job of the same session),
or last when it is left out. Only the order inside a session moves (sessions run beside each other anyway); `400` for a `before` outside
its session, `409` once the job (or one it passes) runs or ended. The shell does it by dragging a waiting row in 📋 Tasks (Alt+↑/↓ from the keyboard).
`POST /api/jobs/<id>/parallel` (⚡ parallel send) is for a job that waits only because its session is busy: it moves to a new task (a
session of its own) and starts now. The same choice exists when sending: `POST /api/send {…, parallel: true}` to a task whose session runs or queues a job
makes the message a new task of its own (named after its first line) that starts now; to a free session it is sent as it is
(`first` and `parallel` together are refused).

Two sessions may still touch the same files. A send (`POST /api/send`, also `append` / `edit`) or a ⚡ parallel send whose quotes name a
workspace file or folder (`📄 path`, `📁 path/`, `🧩 path/`) that another session's running job quotes too (the same path, or one inside
the other) is refused with `409 {error, conflict: [{job, task, title, paths}]}` and nothing changes. The shell shows who is editing what
and asks the person; approved, it sends the same request again with `confirm: true`.

`POST /api/upload?path=<folder>&name=<file name>` writes the raw body (not JSON) as a file of the workspace folder `path`, making the
folder when it is missing, and answers `{path}`. It never replaces a file: a taken name becomes `name (2).ext`, `name (3).ext`… It refuses
`403` outside the workspace or inside a protected folder (§6) and `400` for a name with a folder in it, a name the tree hides or a body over 500 MB.
The shell sends one request per file when files or folders from the desktop are dropped on the explorer (on a folder: into it; on a file:
beside it; on the empty space: the workspace root).

## 6. Lock

By default the core is locked: the file tree and file reads stay inside the workspace and never enter the core or data folders,
and agents receive those folders in `protect`. The rule, in order:

1. `<data>/config.json` `core_locked` set to `true` or `false` wins.
2. Otherwise the core is unlocked when the workspace is, or contains, the core's own git clone (the folder holding `aether/`, `spec/`
   and `conformance/`). Opening a folder above the core is how the person says "I am working on the core". A pip install
   (`site-packages`) never unlocks this way: open a clone to edit the core.
3. Otherwise it is locked.

The lock is recomputed when the workspace changes. The shell shows 🔓 or 🔒 with the reason (`/api/info` `lock_reason`) when you hover the version in its header.

The workspace is the person's choice, made in the shell (`POST /api/config {"workspace": "/abs/path"}`, kept in `<data>/config.json`)
or fixed at start (`--workspace`). Until one is set, file and send requests answer 409. Extensions cannot set it: like every shared key,
only the shell writes it (a sandboxed page has an opaque origin and cannot send `X-Aether`).
Each change puts the new folder first in `<data>/config.json` `recent` (the folder left right after it, at most 10, no repeats).
The core writes `recent`, nobody else: it is not a shared key. `/api/info` `recent` lists the ones that still exist, and the shell
offers them in the workspace dialog so one click switches back.

## 7. Not in v0.1

`serve` (a backend process per extension behind `x/<id>/`, HTTP and WebSocket) is planned for v0.2. `render` (§3.2) covers the
one case previews needed now ―― drawing a file once per version ―― without a process that keeps running.
Also planned before 1.0, so that third-party extensions keep working across versions and machines:
settings an extension owns (its own `ext.<id>` space, never the shared keys) · a transition window where the core still accepts the
previous 0.x manifests · `requires` in the manifest (commands, environment variables, Python packages kept inside the extension folder),
checked by `python3 -m aether check` and reported in `/api/info` `errors`.
